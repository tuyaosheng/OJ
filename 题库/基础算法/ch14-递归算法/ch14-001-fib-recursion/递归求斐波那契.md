# 讲解稿：递归求斐波那契（ch14-001）

## 一、题目解读

求斐波那契数列的第 n 项，n ≤ 90。

上一章我们用**递推**（循环）求过它。这一章换个视角——用**递归**。

> **递推 vs 递归：一体两面**
>
> - **递推**：从**小到大**，**自底向上**推。`f[1] → f[2] → f[3] → … → f[n]`
> - **递归**：从**大到小**，**自顶向下**拆。`f(n) → 需要 f(n-1) 和 f(n-2) → 再往下拆……`
>
> **它们描述的是同一个关系式，只是"走"的方向相反。**

## 二、思路分析

### 最朴素的递归：优雅，但致命

递归写法几乎是把数学定义**直接翻译**成代码：

```cpp
long long fib(int n)
{
    if (n <= 2) return 1;               // 边界：F(1) = F(2) = 1
    return fib(n - 1) + fib(n - 2);     // 递归式，和数学定义一模一样
}
```

**三行！** 比循环还短，还漂亮。

**但它会超时。** 而且不是慢一点点，是慢到天荒地老。**为什么？**

### 病根：疯狂的重复计算

我们把 `fib(5)` 的**调用树**画出来：

```
                  fib(5)
                /        \
          fib(4)          fib(3)
         /      \         /     \
    fib(3)    fib(2)  fib(2)   fib(1)
    /    \
 fib(2) fib(1)
```

数一数：
- `fib(3)` 被计算了 **2 次**
- `fib(2)` 被计算了 **3 次**

才 n=5 就这么乱了。n 再大一点：

| n | 朴素递归的调用次数 |
|---|-------------------|
| 10 | 177 |
| 30 | 约 270 万 |
| 45 | 约 36 亿 |
| **90** | 约 **2^90 ≈ 10^27** |

**复杂度是 O(2^n)——指数级爆炸。** n=90 时，即使每秒算一万亿次，也要跑上亿年。

> **为什么会这样？** 因为递归树的每个节点都会分裂成两个子节点，树的规模随深度**指数增长**。而其中**绝大多数节点在重复计算同一件事**。

### 解药：记忆化（Memoization）

思路简单到令人发笑：

> **算过的结果，记下来。下次要用，直接查表，别再算了。**

```cpp
long long memo[95];         // memo[i] 存 F(i)，-1 表示"还没算过"

long long fib(int n)
{
    if (n <= 2) return 1;

    if (memo[n] != -1) return memo[n];       // ★ 查表：算过就直接返回

    memo[n] = fib(n - 1) + fib(n - 2);       // ★ 算完存表
    return memo[n];
}
```

**只加了两行，复杂度从 O(2^n) 骤降到 O(n)。**

**为什么？** 因为现在每个 `fib(i)` **最多只会被真正计算一次**——第一次算完就存进表里，之后所有对它的调用都是 O(1) 的查表。

一共只有 n 个不同的子问题，所以总共只做 O(n) 次真正的计算。

那棵枝繁叶茂的指数级递归树，被"剪"成了一条细长的线。

## 三、代码讲解

```cpp
const int N = 95;
long long memo[N];

long long fib(int n)
{
    if (n <= 2) return 1;               // 递归边界，缺了它会无限递归
    if (memo[n] != -1) return memo[n];  // 记忆化查表
    memo[n] = fib(n - 1) + fib(n - 2);  // 计算并存表
    return memo[n];
}

int main()
{
    int n; cin >> n;
    for (int i = 0; i < N; i++) memo[i] = -1;   // 初始化为"未计算"
    cout << fib(n) << "\n";
}
```

### 为什么用 −1 标记而不是 0？

本题中 F(n) 恒为正，所以用 `memo[n] != 0` 来判断"是否算过"，其实也能正常工作。

但这是个**坏习惯**。设想另一道题，某个子问题的答案**本身就是 0**，那么"值为 0"和"还没算过"就分不清了，程序会反复重算它（甚至陷入死循环）。

**用一个"不可能出现的值"（如 −1）作标记，是更严谨的做法。** 养成好习惯。

### 数据范围

- F(90) = **2880067194370816120** ≈ 2.9 × 10^18
- `long long` 上限 ≈ 9.2 × 10^18 —— **刚好装得下**（F(93) 就溢出了）
- 用 `int`？F(47) 就爆了。

## 四、易错点

1. **写朴素递归不加记忆化** —— O(2^n)，n=90 必然 TLE。**本题的核心考点。**
2. **忘记初始化 `memo` 为 −1** —— 默认全 0，会被误认为"已算过，结果是 0"，返回一堆 0。
3. **边界写成 `n <= 1`** —— F(2) 会被错误地递归下去。应该是 `n <= 2 return 1`。
4. **用 `int`** —— F(47) 就溢出了。
5. **忘记边界，导致无限递归** —— 栈溢出（Runtime Error）。

## 五、小结

### 递归的三要素

写任何递归，都要想清楚这三件事：

| 要素 | 本题 |
|------|------|
| **① 递归边界**（什么时候停？） | `n <= 2` 时返回 1 |
| **② 递归式**（怎么把大问题拆成小问题？） | `fib(n) = fib(n-1) + fib(n-2)` |
| **③ 返回值**（每层返回什么？） | 第 n 项的值 |

**缺了边界 → 无限递归、爆栈。** 这是初学者最常见的死法。

### 记忆化：递归与 DP 的桥梁

**记忆化搜索**是个了不起的技巧：

> **它让你用【递归的写法】（自然、贴近问题定义），达到【递推的效率】（不重复计算）。**

事实上，**记忆化搜索 = 动态规划**，只是实现方式不同：

| | 记忆化搜索 | 递推式 DP |
|---|-----------|----------|
| 方向 | 自顶向下（从 n 往下拆） | 自底向上（从 1 往上推） |
| 写法 | 递归函数 + 查表 | 循环 + 数组 |
| 效率 | 相同 | 相同 |
| 优点 | 思路自然，只算用得到的状态 | 无递归开销，不会爆栈 |

**很多复杂 DP 题，用记忆化搜索写会比推递推式简单得多**——因为你只需要写出"状态转移"，不用操心"按什么顺序计算"。

### 一个重要的领悟

**递归本身没有错，错的是"重复计算"。**

朴素递归慢，不是因为"递归"这种形式慢，而是因为它**做了大量无用功**。加上记忆化后，它和循环一样快。

**下一题**我们会看到递归的一个"循环做不到"的**独门绝技**：利用"返回途中"的执行顺序，**天然实现倒序输出**。
